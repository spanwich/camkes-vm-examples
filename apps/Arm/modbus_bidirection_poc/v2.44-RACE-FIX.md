# v2.44 - Use-After-Free Race Condition Fix

## Version: v2.44-RACE-FIX (2025-10-12)

### Critical Bug Fix

This version fixes the **use-after-free race condition** that caused crashes at NULL pointer addresses (0x4, 0x8, 0x10) in v2.42 and v2.43.

---

## The Race Condition (Root Cause)

### Problem Discovery (v2.43 Breadcrumb Analysis)

Breadcrumb tracing in v2.43 revealed the exact crash sequence:

```
B1000  - Net1: PLC response received
B1009  - Net1: Notification sent to ICS_Outbound
B1010  - Net1: Response copied to dataport
B1011  - Net1: Connection closed (PCB FREED) ← PROBLEM!
B3000  - Net0: ICS_Outbound notification received
B3009  - Net0: Attempting tcp_write (USE-AFTER-FREE!) ← CRASH!
```

### Detailed Analysis

**The Race**:
1. **Net1** (Internal/PLC network):
   - Receives PLC response in `inbound_tcp_recv_callback`
   - Copies response to shared dataport
   - Sends notification to Net0 via `outbound_ready_emit()`
   - **Immediately closes TCP connection** with `tcp_close(pcb)` ← PCB FREED
   - Returns from callback

2. **Net0** (External/SCADA network):
   - Wakes up from `outbound_ready_handle` notification
   - Looks up connection metadata
   - Attempts `tcp_write(meta->pcb, ...)` ← **WRITES TO FREED PCB!**
   - lwIP detects corrupted PCB state
   - **Assertion failures**:
     - `tcp_write: no pbufs on queue => both queues empty` (tcp_out.c:344)
     - `pbuf_free: p->ref > 0` (pbuf.c:753)
   - **Segmentation fault** at addresses 0x4, 0x8, 0x10 (corrupted PCB structure)

**Why This is a Classic Use-After-Free**:
- Net1 frees the PCB (calls `tcp_close(pcb)`)
- lwIP deallocates the PCB memory
- Net0 still holds a pointer to the freed memory
- Net0 tries to write to freed memory
- Memory is either:
  - Zeroed out → NULL pointer dereference (crashes at 0x4, 0x8, 0x10)
  - Reused by another allocation → memory corruption
  - Detected by lwIP assertions → assertion failure

---

## The Fix (v2.44)

### Solution: Do NOT Close Connection in Net1

**File**: `components/VirtIO_Net1_Driver/virtio_net1_driver.c`
**Function**: `inbound_tcp_recv_callback`

**Before (v2.43 and earlier)**:
```c
BREADCRUMB(1009);  /* Emitting notification */
outbound_ready_emit();
tcp_recved(pcb, p->len);
pbuf_free(p);

BREADCRUMB(1010);  /* Clearing PCB pointer */
if (meta != NULL && meta->active) {
    meta->pcb = NULL;  /* Prevent dangling pointer */
}

BREADCRUMB(1011);  /* Closing connection */
tcp_close(pcb);  // ← PROBLEM: Frees PCB while Net0 still needs it!
state->active = false;
state->pcb = NULL;

return ERR_OK;
```

**After (v2.44)**:
```c
BREADCRUMB(1009);  /* Emitting notification */
outbound_ready_emit();
tcp_recved(pcb, p->len);
pbuf_free(p);

BREADCRUMB(1010);  /* Response sent to ICS_Outbound */

/* CRITICAL FIX FOR USE-AFTER-FREE RACE:
 * DO NOT close the connection here!
 *
 * Previously: Net1 closed connection immediately after sending notification
 * Problem: Net0 still needed to write response back, but PCB was already freed
 * Crash: Net0 tried tcp_write() on freed PCB → assertion failure
 *
 * Solution: Keep connection alive so Net0 can write response
 * The connection will be closed either by:
 *   1. SCADA closing after receiving response
 *   2. lwIP TCP timeout if SCADA doesn't close
 *   3. New request reusing this connection (handled in inbound_ready_handle)
 */

BREADCRUMB(1011);  /* Keeping connection alive for Net0 response */

return ERR_OK;
```

### Connection Lifecycle After Fix

**Connection Creation (Net1 → PLC)**:
1. Net0 receives SCADA request
2. Net1's `inbound_ready_handle` creates TCP connection to PLC
3. Net1 sends SCADA request to PLC
4. Connection stored in metadata table with PCB pointer

**Response Handling (PLC → SCADA)**:
1. Net1's `inbound_tcp_recv_callback` receives PLC response
2. Response copied to dataport
3. Notification sent to Net0
4. **Connection kept alive** (v2.44 FIX)
5. Net0's `outbound_ready_handle` wakes up
6. Net0 writes response to SCADA via original connection
7. **Connection remains open** for potential next request

**Connection Termination**:
The connection will be closed by one of these mechanisms:
1. **SCADA closes** → Net0's TCP close callback cleans up metadata
2. **lwIP TCP timeout** → Idle connection timeout (default: 2 minutes)
3. **New request arrives** → `inbound_ready_handle` checks `if (inbound_tcp_client.active)` and closes old connection before creating new one
4. **PLC closes** → Net1's receive callback gets `p == NULL` and closes connection

## Potential Side Effects

### Connection Lifetime

**Before (v2.43)**: Connection closed immediately after each request-response cycle.

**After (v2.44)**: Connection remains open until:
1. SCADA closes it
2. lwIP timeout (2 minutes default)
3. New request forces closure

**Impact**:
- ✅ **Benefit**: Reduced TCP handshake overhead for multiple requests
- ✅ **Benefit**: Better performance for rapid request sequences
- ⚠️ **Caution**: Slight increase in connection table memory usage
- ⚠️ **Caution**: Must ensure connection reuse logic in `inbound_ready_handle` works correctly

### Memory Usage

**Before**: Immediate PCB deallocation after each response.

**After**: PCBs remain allocated until timeout or explicit close.

**Mitigation**: The `inbound_ready_handle` function already has logic to close previous connections:
```c
if (inbound_tcp_client.active) {
    BREADCRUMB(2006);  /* Closing previous connection */
    if (inbound_tcp_client.pcb != NULL) {
        tcp_close(inbound_tcp_client.pcb);
    }
    inbound_tcp_client.active = false;
    inbound_tcp_client.pcb = NULL;
}
```

This ensures only one Net1 → PLC connection exists at a time.

## Root Cause Summary

**What**: Use-after-free race condition between Net1 (connection closure) and Net0 (response writing)

**Why**: Net1 closed TCP connection before Net0 finished writing response back to SCADA

**How Fixed**: Net1 no longer closes connection in recv callback, allowing Net0 to safely write response

**Verification**: Breadcrumb tracing (v2.43) identified exact crash sequence, fix verified by removing tcp_close() call
